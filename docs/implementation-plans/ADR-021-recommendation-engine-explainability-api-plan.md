# ADR-021 Implementation Plan: Recommendation Engine Explainability API

## Objective

Expose recommendation explanations as versioned, deterministic,
machine-readable API payloads generated from the same backend scoring facts that
select and order songs. The API must support public, worship-leader, and admin
audiences; provide UI-friendly rendering metadata; and prevent explanations from
referencing unapproved catalog data, private review notes, copyrighted lyric
excerpts, or LLM-created rationale.

## Subtask 1: Define the versioned `RecommendationExplanation` API contract

### Context

ADR-021 requires recommendation responses to include a stable explanation DTO so
clients can render, test, localize, and audit recommendation rationale without
parsing prose. ADR-010 already owns deterministic scoring facts, and ADR-013
establishes structured explanation facts. This subtask turns those facts into an
external API contract with explicit schema versioning and compatibility rules.

### Prompt

Create or extend the recommendation response contract to attach a versioned
`RecommendationExplanation` object. Define the DTO fields, schema/version naming,
OpenAPI or contract-test representation, and compatibility expectations for
future schema versions. Include top-level request/correlation metadata,
recommendation result identifiers, scoring profile version, catalog snapshot or
version, deterministic tie-break facts where appropriate, and collections for
song, transition, set-level, warning, and diagnostic explanation entries.

### Acceptance criteria

- Recommendation responses can include a `RecommendationExplanation` payload with
  an explicit schema version such as `recommendation_explanation.v1`.
- The contract distinguishes selected-song, adjacent-transition, set-level,
  warning, and diagnostics sections with stable machine-readable field names.
- The payload includes scoring profile version, catalog snapshot/version,
  request policy summary, and deterministic tie-break facts when those facts
  affect ordering or selection.
- Contract tests or schema validation fixtures cover a complete successful
  response, a response with warnings, and a response with admin diagnostics.
- API documentation explains that explanation facts are generated by the
  Recommendation Engine and are not produced by an LLM.

### Restrictions

- Do not make rendered prose the source of truth for explanations.
- Do not introduce an LLM call or client-provided rationale into the explanation
  contract.
- Do not expose internal database entities directly as public API objects.
- Do not ship an unversioned explanation payload.

## Subtask 2: Normalize reason codes, display groups, severity, and localization keys

### Context

ADR-021 requires UI-friendly rendering through stable labels, display groups,
severity, and localization keys. ADR-013 defines explanation fact codes, but API
consumers need a curated reason-code taxonomy that is stable enough for external
clients and translatable without changing recommendation selection logic.

### Prompt

Create a governed reason-code registry for the explainability API. Map each
backend explanation fact emitted by the recommendation engine to an API-safe
reason code, severity, display group, audience visibility, localization key, and
structured value schema. Include codes for item fit, eligibility, theme/scripture
matches, transition facts, energy arc, score components, warnings, tradeoffs,
near-miss diagnostics, and deterministic tie-breaks.

### Acceptance criteria

- Every API explanation entry uses a registered reason code rather than an
  ad hoc string.
- Registered codes include display group, severity, localization key, supported
  audience partitions, and allowed value keys.
- Reason-code tests fail when backend facts are emitted without API registry
  entries.
- Localization can translate reason-code templates without changing the selected
  songs, score calculations, or API fact payload.
- Documentation identifies which codes are stable for clients and how additive
  code changes should be released.

### Restrictions

- Do not let frontend clients invent backend reason codes.
- Do not embed locale-specific prose in the deterministic fact payload as the
  only explanation source.
- Do not overload one reason code with unrelated meanings.
- Do not rename or remove public reason codes without a versioning or migration
  plan.

## Subtask 3: Attach per-song explanations from deterministic scoring and catalog evidence

### Context

ADR-021 requires per-song reason codes, score components, matched metadata
references, warnings, approval references, and theme/scripture evidence based
only on approved tags, curated mappings, and catalog references. The LLM may
parse intent, but it must not select songs or invent rationale.

### Prompt

Implement per-selected-item explanation assembly from ADR-010 scoring components
and ADR-013 item-level facts. For each selected arrangement, include role fit,
score component breakdown, approved catalog metadata references, matched theme
or scripture references, approval/provenance references, relevant warnings, and
safe UI display hints. Ensure song and arrangement identifiers line up with the
recommendation result item.

### Acceptance criteria

- Every selected recommendation item has a song-level explanation entry linked to
  the selected song and arrangement identifiers.
- Score components include stable names, numeric contributions, optional weight
  metadata, and reason codes explaining material positive, neutral, or penalty
  contributions.
- Theme and scripture explanations reference approved taxonomy values, curated
  scripture mappings, or catalog references used by scoring.
- Approval and provenance explanations cite approved catalog evidence without
  exposing private review notes.
- Tests verify that missing, low-confidence, or unused metadata becomes a warning
  or is omitted rather than converted into unsupported claims.

### Restrictions

- Do not claim a song matched a theme, scripture, role, or musical requirement
  unless the deterministic scoring inputs contain that evidence.
- Do not expose copyrighted lyric excerpts in explanation evidence.
- Do not include unapproved songs, inactive arrangements, private doctrinal
  notes, or non-catalog facts.
- Do not recompute or reorder selected songs during explanation assembly.

## Subtask 4: Attach directional transition explanations between adjacent arrangements

### Context

ADR-021 requires directional transition explanations between adjacent
arrangements. These explanations must describe the movement from one selected
item to the next, including key, relative major/minor handling, tempo jumps,
meter, energy, and arrangement compatibility where approved parser-derived data
exists.

### Prompt

Implement transition explanation entries for every adjacent pair in a generated
setlist. Populate each entry from deterministic transition score facts and
arrangement metadata. Include source and target item identifiers, transition
reason codes, score components or penalties, structured values for key/BPM/meter
changes, warnings for accepted tradeoffs, and display metadata for client UI.

### Acceptance criteria

- A setlist with `N` selected items includes `N - 1` directional transition
  explanation entries.
- Transition entries identify source item, target item, source arrangement, and
  target arrangement.
- Same-key, relative major/minor, key-center, BPM jump, meter compatibility,
  energy movement, and accepted tradeoff reasons can be represented with stable
  reason codes and structured values.
- Parser-derived compatibility facts include parser confidence or evidence
  references when available.
- Tests cover allowed transitions, penalized transitions, accepted tempo
  tradeoffs, missing metadata warnings, and deterministic ordering of transition
  entries.

### Restrictions

- Do not create transition facts from unavailable arrangement metadata.
- Do not hide policy violations or penalties that affected the selected order.
- Do not treat transitions as unordered pairs; explanations must be directional.
- Do not change selection or ordering when transition explanation detail is
  requested.

## Subtask 5: Attach set-level energy arc, request-policy, and coverage explanations

### Context

ADR-021 requires energy arc explanations for the selected setlist shape and
summary explanations for how the response satisfied request constraints. The
payload should help users understand counts, key centers, tempo policy,
theme/scripture coverage, defaults, and compromises without suggesting the LLM
selected songs.

### Prompt

Generate set-level explanation entries from the final recommendation result,
request slots, applied defaults, scoring profile, energy arc evaluator, and
constraint diagnostics. Include counts, praise/worship role distribution,
key-center summary, tempo policy summary, energy arc shape, theme/scripture
coverage, applied defaults, and warnings for catalog limitations or accepted
tradeoffs.

### Acceptance criteria

- Set-level explanations include selected counts versus requested counts,
  key-center policy outcome, tempo policy outcome, and energy arc rationale.
- Applied defaults such as `10 praise + 5 worship`, same-key preference,
  relative major/minor allowance, maximum key centers, and maximum BPM jump are
  represented when they influenced the result.
- Theme/scripture coverage is based only on approved taxonomy values, curated
  mappings, or catalog references used by scoring.
- Warnings distinguish fully satisfied constraints from relaxed constraints,
  insufficient-catalog scenarios, and accepted tradeoffs.
- Tests cover default requests, explicit policy overrides, partially satisfied
  requests, and insufficient eligible catalog fixtures.

### Restrictions

- Do not state that every constraint was satisfied if the engine accepted a
  compromise.
- Do not infer pastoral meaning beyond approved taxonomy and curated mappings.
- Do not include hidden candidate lists in public set-level explanations.
- Do not use free-form LLM summaries as set-level explanation facts.

## Subtask 6: Enforce audience partitioning and safe redaction

### Context

ADR-021 requires audience-partitioned fields for public, worship leader, and
admin diagnostics. Public explanations must omit admin-only diagnostics, private
review notes, sensitive provenance payloads, and unapproved catalog data while
still exposing enough deterministic rationale for trust and UI rendering.

### Prompt

Implement audience-aware explanation filtering for public, worship-leader, and
admin consumers. Add authorization or request-mode handling that chooses the
allowed explanation sections and fields without changing the recommendation
selection result. Define redaction rules for diagnostics, candidate exclusions,
near misses, review data, provenance details, and scoring internals.

### Acceptance criteria

- Public responses redact admin-only diagnostics and private review details.
- Worship-leader responses can include operationally useful fit, transition, and
  warning facts without exposing sensitive admin-only data.
- Admin responses can include candidate exclusions, near misses, hard-filter
  reasons, score ranges, tie-break details, and constraint-relaxation rationale
  when authorized.
- Tests verify that audience mode changes only explanation visibility, not
  selected songs, ordering, or scores.
- Security or authorization tests cover unauthorized attempts to request admin
  diagnostics.

### Restrictions

- Do not leak private review notes, sensitive provenance payloads, unapproved
  songs, copyrighted lyric excerpts, or raw connector data to public or
  worship-leader audiences.
- Do not recompute recommendations differently for admin explanation mode.
- Do not rely on frontend hiding as the only redaction mechanism.
- Do not log redacted sensitive fields in public request traces.

## Subtask 7: Add deterministic reproducibility, fixtures, and regression tests

### Context

ADR-021 acceptance criteria require re-running the same request against the same
catalog snapshot and scoring profile to produce the same explanation payload.
Because explanation data includes scores, warnings, and tie-break facts,
regression fixtures must make nondeterminism visible.

### Prompt

Create deterministic fixture tests and snapshot/regression coverage for the
explainability API. Use fixed catalog snapshots, scoring profiles, request
payloads, and audience modes. Assert stable selected results and stable
explanation payloads, including ordering of arrays, numeric score precision,
reason codes, warning codes, and redaction behavior.

### Acceptance criteria

- Tests prove identical request, catalog snapshot, scoring profile, and audience
  mode produce identical explanation payloads.
- Fixture coverage includes public, worship-leader, and admin explanation
  responses for the same underlying recommendation.
- Regression tests cover exact tie-breaks, near ties, score component precision,
  transition ordering, warnings, and redacted fields.
- Schema or contract tests validate representative payloads against the
  published API contract.
- Test data uses approved fixture catalog entries and avoids copyrighted lyric
  excerpts.

### Restrictions

- Do not use wall-clock time, random UUIDs, unordered collection iteration, or
  database default row order in explanation payload generation.
- Do not make tests depend on network access or external catalog services.
- Do not bless nondeterministic snapshots by updating expected fixtures without
  identifying the source of drift.
- Do not include real sensitive review/provenance content in fixtures.

## Subtask 8: Document API usage, migration rules, and operational safeguards

### Context

ADR-021 introduces a client-facing API contract that impacts web clients, audit
views, localization, diagnostics, and future schema evolution. Teams need usage
documentation, migration guidance, and operational safeguards so explanation
changes remain deterministic, safe, and compatible.

### Prompt

Publish documentation for the explainability API, including payload examples,
audience-mode behavior, reason-code registry ownership, localization workflow,
schema-version migration rules, redaction guarantees, and troubleshooting
instructions. Update the implementation-plan index and any architecture or API
documentation that points clients to recommendation response contracts.

### Acceptance criteria

- Documentation includes public and admin example payloads that demonstrate song,
  transition, set-level, warning, and diagnostic explanation sections.
- Migration guidance explains how to add reason codes, evolve schema versions,
  deprecate fields, and keep localization templates in sync.
- Operational guidance describes how to investigate explanation drift, redaction
  failures, missing catalog evidence, and scoring-profile changes.
- Architecture or API docs clearly state that explanation facts are generated by
  backend deterministic logic and never by LLM song selection.
- The implementation-plans README links to this ADR-021 plan in the appropriate
  phase/order section.

### Restrictions

- Do not document unstable internal implementation details as public guarantees.
- Do not provide examples that include unapproved songs, private notes,
  copyrighted lyric excerpts, or invented catalog facts.
- Do not imply localization templates are allowed to add new factual claims.
- Do not leave ADR-021 unlinked from the implementation-plan index.
