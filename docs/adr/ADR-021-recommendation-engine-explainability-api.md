# ADR-021: Recommendation Engine Explainability API

Status: Accepted  
Date: 2026-05-28

## Context

ADR-010 requires deterministic scoring and ADR-013 establishes explanations as a product capability. Phase 4 needs a stable API contract so web clients, audit views, and future localization layers can render explanations without relying on prose generated by an LLM.

## Problem

If recommendation explanations are emitted as ad hoc text, Cadentia cannot reliably test them, localize them, compare them across releases, or prove that they reference approved catalog evidence only. Free-form explanations also risk implying that the LLM participated in song selection.

## Decision

Expose recommendation explanations as versioned, machine-readable DTOs generated by the Recommendation Engine from the same deterministic scoring facts used to select and order songs. The explanation API will return reason codes, score components, transition facts, theme/scripture evidence, approval references, and UI rendering hints.

Explanation generation must not perform an additional LLM call. User-facing copy may be rendered from templates keyed by reason code and locale, but the underlying explanation facts remain deterministic and reproducible.

## Requirements

- Define a versioned `RecommendationExplanation` DTO attached to recommendation responses.
- Include per-song reason codes, score components, matched metadata references, and warnings.
- Include directional transition explanations between adjacent arrangements.
- Include theme and scripture explanations based only on approved tags, curated mappings, and catalog references.
- Include energy arc explanations for the selected setlist shape.
- Include scoring profile version, catalog snapshot/version, and deterministic tie-break facts where appropriate.
- Support audience-partitioned fields for public, worship leader, and admin diagnostics.
- Support UI-friendly rendering through stable labels, display groups, severity, and localization keys.
- Prevent explanations from referencing unapproved songs, private review notes, copyrighted lyric excerpts, or non-catalog facts.

## Acceptance Criteria

- Recommendation responses include structured explanations for selected songs and transitions.
- Re-running the same request against the same catalog snapshot and scoring profile produces the same explanation payload.
- Explanations reference real catalog metadata, approved taxonomy values, and approved arrangement data only.
- Public explanation payloads redact admin-only diagnostics.
- Localization can be added by translating reason-code templates without changing recommendation selection.

## Consequences

Positive:

- Clients can render consistent explanation UI without parsing prose.
- Explanations are testable and suitable for audits.
- Localization and accessibility can evolve independently of recommendation logic.
- The LLM/REng boundary remains explicit.

Tradeoffs:

- DTO versioning and migration discipline are required.
- Scoring changes must update explanation fixtures.
- Some nuanced pastoral rationale may need curated reason codes rather than generated prose.

## Alternatives Considered

1. Generate natural-language explanations with the LLM after selection.
   - Rejected: nondeterministic and risks introducing unsupported claims.
2. Return only final numeric scores.
   - Rejected: insufficient for worship leader trust and operational debugging.
3. Store explanation text in the catalog.
   - Rejected: explanations depend on request context, transitions, and scoring profile.

## Open Questions

- Which reason-code taxonomy should be considered stable for external clients?
- Should near-miss explanations be part of the default response or admin-only diagnostics?
- How many historical explanation schema versions must be supported?
