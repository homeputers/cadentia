# ADR-021: Recommendation Engine Explainability API

Status: Accepted  
Date: 2026-05-28

## Context

ADR-010 requires deterministic scoring and ADR-013 establishes explanations as a product capability. Phase 4 needs a stable API contract so web clients, audit views, and future localization layers can render explanations without relying on prose generated by an LLM.

## Problem

If recommendation explanations are emitted as ad hoc text, Cadentia cannot reliably test them, localize them, compare them across releases, or prove that they reference approved catalog evidence only. Free-form explanations also risk implying that the LLM participated in song selection.

## Decision

Expose recommendation explanations as versioned, machine-readable DTOs generated by the Recommendation Engine from the same deterministic scoring facts used to select and order songs. The explanation API will return reason codes, score components, transition facts, theme/scripture evidence, approval references, and UI rendering hints.

Explanation generation must not perform an additional LLM call. User-facing copy may be rendered from templates keyed by reason code and locale, but the underlying explanation facts remain deterministic and reproducible.


## API Contract Versioning

Recommendation responses may attach a versioned `RecommendationExplanation` object
whose v1 schema identifier is `recommendation_explanation.v1`. The payload is an
external API contract, not rendered prose. Clients should render localized copy
from `templateKey`, `code`, `values`, and `evidence`, but must not parse
`defaultText` or any other prose as the source of truth.

The v1 payload includes:

- top-level request and tracing metadata: `requestId`, optional `correlationId`,
  `recommendationResultId`, optional `setlistId`, and `generatedAt`;
- deterministic generation metadata: `generatedBy: RecommendationEngine`,
  `scoringProfileVersion`, and `catalogSnapshotVersion`;
- `requestPolicySummary` with counts, key policy, tempo policy, extracted theme
  and scripture hints, optional service policy fields, and applied backend
  defaults;
- `deterministicTieBreaks` for tie-break rules that affected ordering or
  selection;
- separate machine-readable collections named `selectedSongs`,
  `adjacentTransitions`, `setLevel`, `warnings`, and `diagnostics`.

Compatibility rules for `recommendation_explanation.v1` are additive-only:
optional fields and enum values may be added, but existing public field names,
required fields, and meanings must not be removed or renamed. Breaking changes
require a new `schemaVersion` and a documented migration window. Admin
diagnostics remain audience-partitioned and must be redacted from public
responses.

Explanation facts are generated by the deterministic Recommendation Engine from
scoring, policy, transition, and approved catalog evidence. They are not produced
by an LLM, are not client-supplied rationale, and do not expose internal database
entities directly as public API objects.


## Governed Reason-Code Registry

Every explanation entry in `recommendation_explanation.v1` must use a reason
code from the governed registry. The registry is owned by the backend
Recommendation Engine and exported through the API contract package; frontend
clients may choose which registered entries to render, but must not invent new
backend reason codes or reinterpret a code for an unrelated meaning.

Each registry entry includes:

- `code`: stable API-safe reason code;
- `displayGroup`: UI grouping such as `theme_scripture`, `transitions`,
  `energy_arc`, `score_components`, `warnings`, `tradeoffs`, `near_miss`, or
  `tie_breaks`;
- allowed `severity` values: `info`, `warning`, or `blocked`;
- supported audience partitions: `public`, `worship_leader`, and/or `admin`;
- `localizationKey`: the template lookup key used by localization bundles;
- `allowedValueKeys`: the structured payload keys that templates may reference;
- `stableForClients`: whether clients may rely on the code across compatible v1
  releases.

Backend fact-code mapping is one-to-one unless the coverage matrix explicitly
marks an internal signal as omitted. Theme and scripture matches use separate
reason codes, transition facts use directional transition reason codes, score
components use score-component reason codes, warning and tradeoff codes remain
separate, near-miss diagnostics are admin partitioned, and deterministic
tie-breaks use `DETERMINISTIC_TIE_BREAK_APPLIED`.

Localization bundles translate templates by `localizationKey` and interpolate
only `allowedValueKeys`. Translating or changing template prose must never change
selected songs, score calculations, deterministic tie-breaks, or the structured
fact payload. Locale-specific prose must not be embedded in the deterministic
fact payload as the only explanation source.

Reason-code lifecycle rules:

- adding a new active code, value key, display group, or audience partition is an
  additive `recommendation_explanation.v1` change and should be released with
  fixtures and documentation;
- public codes marked `stableForClients` must not be renamed or removed within
  v1;
- narrowing severity, audience, scope, or value keys is breaking and requires a
  new schema version or a documented migration window with deprecation metadata;
- replaced codes must remain parseable until the migration window closes and
  must identify the replacement code.

## Requirements

- Define a versioned `RecommendationExplanation` DTO attached to recommendation responses.
- Include per-song reason codes, score components, matched metadata references, and warnings.
- Include directional transition explanations between adjacent arrangements.
- Include theme and scripture explanations based only on approved tags, curated mappings, and catalog references.
- Include energy arc explanations for the selected setlist shape.
- Include scoring profile version, catalog snapshot/version, and deterministic tie-break facts where appropriate.
- Support audience-partitioned fields for public, worship leader, and admin diagnostics.
- Support UI-friendly rendering through stable labels, display groups, severity, and localization keys.
- Prevent explanations from referencing unapproved songs, private review notes, copyrighted lyric excerpts, or non-catalog facts.

## Acceptance Criteria

- Recommendation responses include structured explanations for selected songs and transitions.
- Re-running the same request against the same catalog snapshot and scoring profile produces the same explanation payload.
- Explanations reference real catalog metadata, approved taxonomy values, and approved arrangement data only.
- Public explanation payloads redact admin-only diagnostics.
- Localization can be added by translating reason-code templates without changing recommendation selection.

## Consequences

Positive:

- Clients can render consistent explanation UI without parsing prose.
- Explanations are testable and suitable for audits.
- Localization and accessibility can evolve independently of recommendation logic.
- The LLM/REng boundary remains explicit.

Tradeoffs:

- DTO versioning and migration discipline are required.
- Scoring changes must update explanation fixtures.
- Some nuanced pastoral rationale may need curated reason codes rather than generated prose.

## Alternatives Considered

1. Generate natural-language explanations with the LLM after selection.
   - Rejected: nondeterministic and risks introducing unsupported claims.
2. Return only final numeric scores.
   - Rejected: insufficient for worship leader trust and operational debugging.
3. Store explanation text in the catalog.
   - Rejected: explanations depend on request context, transitions, and scoring profile.

## Open Questions

- Should near-miss diagnostics ever be promoted from admin-only diagnostics to worship-leader-visible warnings?
- How many historical explanation schema versions must be supported after a breaking migration?
