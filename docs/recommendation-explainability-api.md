# Recommendation Explainability API Usage and Operations

This document is the client and operator guide for the ADR-021 recommendation
explainability API. It complements the ADR contract by showing how web clients,
audit views, localization maintainers, and operators should consume, migrate, and
troubleshoot explanation payloads.

## Public contract summary

Recommendation responses may include an `explanation` object with
`schemaVersion: "recommendation_explanation.v1"`. The object is a structured API
contract, not generated prose. Explanation facts are generated by backend
Recommendation Engine logic from deterministic scoring output, policy checks,
transition facts, and approved catalog evidence. The LLM intent parser may
extract request slots, but it never selects songs and never creates explanation
facts.

Clients must treat these fields as the stable rendering inputs:

- `schemaVersion`
- `audience`
- `scoringProfileVersion`
- `catalogSnapshotVersion`
- `requestPolicySummary`
- `selectedSongs`
- `adjacentTransitions`
- `setLevel`
- `warnings`
- `diagnostics`
- `deterministicTieBreaks`

Localized UI copy must be rendered from registered reason-code templates using
`templateKey`, `code`, `values`, and `evidence`. Do not parse or persist rendered
copy as the source of truth.

## Audience modes and redaction behavior

| Audience | Intended consumer | Included explanation detail | Required redactions |
| --- | --- | --- | --- |
| `public` | Congregation-facing views, printed plans, non-admin clients | Approved selected-song rationale, safe transition rationale, set-level summaries, public warnings | Admin diagnostics, near-miss candidates, private review notes, sensitive provenance payloads, unapproved catalog data, raw connector payloads, copyrighted lyric excerpts |
| `worship_leader` | Planning UI for authorized team leaders | Public facts plus operational warnings, score component summaries, metadata-confidence warnings, accepted tradeoffs | Admin-only candidate exclusions, private review notes, raw provenance bodies, unapproved songs |
| `admin` | Authorized audit and catalog-maintenance views | Public and worship-leader facts plus candidate exclusions, near misses, approval/provenance gate diagnostics, tie-break diagnostics | Private notes remain private unless the caller is explicitly authorized for the separate review-note surface; copyrighted lyrics and raw connector payloads are never exposed through explanations |

Changing `audience` must change only which explanation entries and fields are
visible. It must not change selected songs, song order, scores, tie-breaks, or
catalog eligibility.

## Reason-code registry ownership

The backend Recommendation Engine owns the reason-code registry and exports it
through the API contract package. Frontend clients, localization bundles, and
audit views may decide which registered entries to display, but they must not
invent backend reason codes or reinterpret a code for unrelated facts.

A registry entry must define:

- the stable `code`;
- `displayGroup`;
- allowed `severity` values;
- allowed audience partitions;
- `templateKey` / `localizationKey`;
- allowed `values` keys;
- stability and deprecation metadata when applicable.

## Localization workflow

1. Backend adds or updates the registry entry and allowed value keys.
2. Contract fixtures are updated for each affected audience mode.
3. Localization bundles add templates for every supported locale before the code
   is made visible in production UI.
4. Template validation checks that every placeholder maps to an allowed value key
   and that no unused placeholders remain.
5. Reviewers verify that translated text does not introduce new factual claims,
   doctrinal interpretations, song titles, lyric excerpts, or evidence not
   present in the structured payload.

Localization templates may change tone, grammar, and ordering of existing facts.
They must not add claims beyond `values` and `evidence`, and they must not alter
recommendation selection, score calculation, redaction, or tie-break behavior.

## Migration rules

### Adding a reason code

Adding a reason code is compatible within `recommendation_explanation.v1` when
it is additive:

1. Add the code to the backend-owned registry with display group, severity,
   audience, localization key, allowed value keys, and stability metadata.
2. Add deterministic fixture coverage for public, worship-leader, and admin
   visibility as applicable.
3. Add localization templates for all supported locales or keep the code hidden
   from localized UI until templates are ready.
4. Update client rendering documentation when the code needs a new UI treatment.
5. Verify that the new code references only approved catalog evidence and does
   not change selected songs.

### Evolving schema versions

Use additive v1 evolution for optional fields, optional enum values, and new
reason codes. Create a new schema version when a change removes or renames a
public field, changes the meaning of a required field, narrows audience
visibility for stable public facts, changes numeric semantics, or requires
clients to render an existing code differently.

A breaking migration must include:

- a new `schemaVersion` identifier;
- side-by-side contract fixtures for the old and new versions;
- a documented migration window;
- client fallback behavior;
- a retirement date for the old version;
- monitoring for version adoption and parse failures.

### Deprecating fields or codes

Do not remove a stable public field or code inside v1. Mark it deprecated in the
registry or schema documentation, identify the replacement field/code, emit both
old and new values during the migration window when safe, and keep old fixtures
until client adoption is complete. Narrowing value keys, severity, or audience
visibility is treated as breaking unless the field/code was explicitly marked
experimental and not stable for clients.

### Keeping localization templates in sync

Localization sync is part of the release checklist. A release that adds a
visible code or value key must fail contract validation if any enabled locale is
missing the corresponding template or includes placeholders outside
`allowedValueKeys`. Template-only changes require no schema migration, but they
still require review for factual neutrality and redaction safety.

## Operational safeguards and troubleshooting

### Explanation drift

Use drift checks when the same request, catalog snapshot, scoring profile,
audience mode, and schema version produce different explanation payloads.

1. Confirm the compared payloads have the same `catalogSnapshotVersion`,
   `scoringProfileVersion`, `schemaVersion`, and `audience`.
2. Compare selected result item IDs and order before comparing explanations.
3. Inspect deterministic tie-break entries for changed rules or affected result
   IDs.
4. Check for nondeterministic ordering in arrays, maps, score-component lists,
   warning lists, and diagnostic lists.
5. Verify numeric score precision and rounding rules.
6. Re-run contract fixtures before updating expected snapshots. Never bless a
   changed fixture until the source of drift is understood and documented.

### Redaction failures

Treat any public or worship-leader payload containing admin diagnostics, private
review notes, raw provenance bodies, unapproved catalog references, raw connector
payloads, or copyrighted lyric excerpts as a release-blocking safety issue.

1. Capture the `requestId`, `recommendationResultId`, `audience`, and
   `schemaVersion`.
2. Verify authorization and audience-mode selection at the API boundary.
3. Re-run the same recommendation in public and admin modes and diff only the
   explanation sections.
4. Confirm backend redaction occurs before serialization, logging, caching, and
   response delivery.
5. Check contract tests for the leaked reason code or field and add a regression
   fixture before closing the incident.

### Missing catalog evidence

Every selected-song, transition, theme/scripture, warning, and diagnostic fact
that cites evidence must resolve to approved catalog evidence or approved
aggregate summaries appropriate for the audience.

1. Identify the failing `code`, `values`, and `evidence.ref`.
2. Confirm the selected song or arrangement remains approved and active in the
   catalog snapshot used by the response.
3. Confirm the referenced tag, scripture mapping, arrangement metadata,
   approval, or provenance summary is present in that snapshot.
4. If evidence is missing, block public rendering of the affected fact or emit a
   safe warning rather than fabricating a rationale.
5. Repair catalog data or scoring evidence extraction, then add fixture coverage
   for the missing-evidence case.

### Scoring-profile changes

Scoring changes can legitimately alter scores, selected songs, warnings, and
explanations. They must still be reproducible and reviewable.

1. Bump or record the `scoringProfileVersion` whenever scoring weights,
   eligibility rules, tie-break rules, score components, or precision rules
   change.
2. Update deterministic fixtures for each audience mode with a changelog entry
   explaining the scoring-profile impact.
3. Verify reason-code coverage for any new score component or warning.
4. Confirm localization templates for newly visible facts are available before
   release.
5. Monitor recommendation deltas and explanation parse errors after deployment.

## Client integration checklist

- Request only the audience mode authorized for the current user.
- Render from structured fields and localization templates, not generated prose.
- Preserve `requestId`, `recommendationResultId`, `schemaVersion`,
  `catalogSnapshotVersion`, and `scoringProfileVersion` in client-side error
  reports.
- Treat unknown additive reason codes as ignorable unless the schema marks them
  required for rendering.
- Never display diagnostics from a cached admin response in a public or
  worship-leader context.
- Do not infer additional song facts, lyric content, doctrinal claims, or
  pastoral rationale beyond the structured `values` and `evidence` supplied by
  the backend.
